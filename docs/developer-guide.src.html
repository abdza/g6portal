g6portal · developer guide

Building modules on g6portal

g6portal is a Grails 6 application that is also a runtime for business applications you build by configuration rather than by writing Grails code. This guide walks the whole path: what the pieces are, how to get an instance running from a jar, and how to build a working module end to end — every screenshot below is from that build.

Applies to Grails 6.2.2 · Java 11 Worked example a helpdesk module Audience new portal developers

01The big picture

Two layers, and almost all your work happens in the second one.

Most Grails applications are one layer: you write domain classes, controllers and GSPs, compile, and deploy. g6portal is two.

The platform is the Grails code in grails-app/. It has about thirty domain classes, thirty controllers and thirty services, and it changes rarely. Nothing in it knows what a helpdesk ticket or a leave application is.

A module is the business application — helpdesk, claims, quizzes. A module is not code. It is a set of rows in the platform's own tables: a PortalModule row, some PortalTracker rows with their fields and statuses and transitions, some PortalPage rows whose content is GSP text stored in a column, some UserRole rows. You create those rows through the portal's own admin screens, and you can export the whole set to a ZIP file and import it somewhere else.

That is the single most important thing to understand before you start. When you "write a module" you are filling in forms, not editing files. The GSP and Groovy you write lives in database columns and is compiled at request time. It also means a module travels: the same package installs on a laptop, a test server and a client site, and a portal can ship with modules already inside it.

Everything is namespaced by module

Almost every row in the platform carries a module string. A page is helpdesk / dashboard, a tracker is helpdesk / ticket, a role grant is (this user, module helpdesk, role Agent). There is no foreign key to PortalModule — the module is just a name, and the PortalModule row exists so the export, import and permission screens have something to hang off. Two consequences follow:

  • A typo in a module name creates a second, invisible module. Slugs and module names are matched exactly.
  • Deleting a PortalModule row does not sweep up everything that named it. Pages, trackers and menu nodes carrying that module name stay where they are.

Three kinds of thing you will build

Tracker
A form, a list, a table and (optionally) a workflow. Use one whenever the module stores records that people create, search, edit and move through states.
Page
Arbitrary GSP with Groovy behind it. Use one for anything a tracker's generated screens can't express: dashboards, reports, custom forms, JSON and XLSX endpoints, HTMX fragments.
Menu
Tree nodes that put the above in the header megamenu and a per-module sidebar. Declared as menulist.json in the package.

Where a tracker's data actually lives

A tracker does not store its records in a generic key/value table. It creates and maintains a real table of its own:

trak_<module>_<slug>_data      -- one column per field, plus id and record_status
trak_<module>_<slug>_updates   -- the audit trail, for tracker_type = 'Tracker'

So helpdesk / ticket becomes trak_helpdesk_ticket_data. Adding a field adds a column; adding an index adds an index. That is what makes it reasonable to write plain SQL against a tracker from a page, and it is why the Update DB button in section 7 matters.

The system columns on every data table are id and record_status (the status name, as text). The trail table carries record_id, update_date, updater_id, status, changes and description.

03The URL space

Learn these five shapes and you can navigate any g6portal instance without the menus.

URLGoes toNotes
/view/<module>/<slug>A page, rendered in the site layoutUp to three extra path segments arrive as params.arg1–arg3.
/run/<module>/<slug>A runable page — Groovy executed, result returnedSame extra-segment rule. This is how HTMX fragments, JSON APIs and file downloads are served.
/<module>/<slug>/listA tracker's list screenAlso /create, /display/<id>, /edit/<id>.
/<module>/<slug>/<transition>/<id>Runs a named transition on a recordGET shows the form, POST applies it. Append /direct to skip the form.
/download/<module>/<slug>A FileLink/download/<slug> alone means module portal.
/svc/<module>/<slug>/...A PortalEndpointEverything after the slug belongs to the handler. Authenticates itself; the interceptor does not see it.
/setupFirst-run administrator creationRefuses to do anything once an administrator exists.
/The page portal / homeThe dashboard. It is an ordinary PortalPage, so you can edit it.

What happens on every request

  1. SecurityHeadersInterceptor sets the CSP.

    script-src 'self'. Any external CDN is silently blocked — serve libraries from grails-app/assets/ instead.

  2. SecurityInterceptor resolves the user and writes an audit row.

    The audit row is written before any permission check, so portal_audit_trail records attempts as well as successes. A polling page writes a row per poll; plan for the growth.

  3. It decides whether you may proceed.

    A system administrator with the enablesuperuser setting on is waved through. Otherwise the check depends on the controller: pages are matched against the page's allowedroles, trackers against the tracker's, files against the file's. A Developer on the named module is admitted to the admin screens for that module.

  4. The controller runs.

    For a page that means compiling its content as a GSP template (or evaluating it as a Groovy script, if the page is runable) with a fixed set of variables in scope — see section 10.

04From jar to login

A brand new instance, from an empty directory to a working administrator account.

What you need first

Java 11
The build targets Java 11 and the jar runs on it. Newer JDKs are not tested and Hibernate's reflection will complain on some of them. java -version should say 11.
A jar
One of the three database flavours below.
A port
9090 by default.

Getting a jar

If you have the source, packageall.sh builds all three flavours by swapping grails-app/conf/application.yml for the matching profile and running bootJar:

./packageall.sh
# -> build/libs/g6portal-h2.jar
# -> build/libs/g6portal-postgresql.jar
# -> build/libs/g6portal-mssql.jar

For a single build against whatever application.yml currently says:

export JAVA_HOME=/path/to/java-11
./gradlew bootJar
# -> build/libs/g6portal-0.1.jar   (~180 MB; the asset compile takes a few minutes)

The three jars differ only in their bundled application.yml — the JDBC driver, the URL and the dialect. If you are going to supply your own configuration file anyway, any of them will do.

Lay out the directory

The jar resolves relative paths against its working directory, not against itself. Give it a directory of its own:

g6portal/
  g6portal-h2.jar
  application.yml         # optional: overrides the config baked into the jar
  bundled-modules/        # optional: module ZIPs imported at first boot
  # created on first run:
  g6db.mv.db              # the H2 database file
  setup-token.txt         # the one-time first-run token
  uploads/                # uploads and module export/import staging
Choose the directory deliberately

H2 keeps its whole database in g6db.mv.db in that directory, and locks the file to a single process. Two instances started from the same directory will fight; a test run pointed at the same file will write to real data.

Start it

cd g6portal
java -jar g6portal-h2.jar

The console prints a banner you need to read:

******************************************************************************
* This instance has no system administrator yet.
*
* Open  /setup  and enter this token to create the first administrator:
*
*     38ccd8fd4307117f214d3932fb610905d24869f021b762f1
*
* It is also in:  /home/you/g6portal/setup-token.txt
* That file is deleted as soon as the administrator account exists.
******************************************************************************

Grails application running at http://localhost:9090/ in environment: production
Why a token

A fresh database has no accounts, and every controller sits behind the security interceptor — so there is nobody who could be authorised to create the first user. The token proves you have filesystem access to the machine running the portal, which is the only credential that exists at that moment. It is written to a file readable only by the portal's own account, and deleted the instant the administrator exists.

Create the first administrator

Open http://localhost:9090/setup. The page tells you where the token file is, in case you missed the console.

  1. Paste the token.

    From the console or from setup-token.txt. Five wrong attempts and the page makes you restart the browser session.

  2. Pick a User ID.

    This is the login username. No spaces — it has to be typeable into the login form.

  3. Fill in name, email and a password of at least eight characters.

  4. Leave Treat system administrators as Admin of every module ticked.

    This writes the enablesuperuser setting. Without it, isAdmin only carries the checks that test it directly, and you will find yourself locked out of your own module's pages until you grant yourself a role by hand. On a new instance you want it on.

If server.disable_lanid is not set

Accounts that have a LAN ID authenticate against Active Directory, not against a local password. The administrator you create here has no LAN ID, so it signs in with the password you just set — the setup screen says so explicitly when the setting is off.

Log in

Expand Admin in the sidebar and you have the whole platform:

Choosing a database

FlavourJDBC URLUse for
H2jdbc:h2:./g6db;LOCK_TIMEOUT=10000;DB_CLOSE_ON_EXIT=FALSE;DATABASE_TO_LOWER=TRUE;MODE=PostgreSQLDevelopment, demos, single-user instances. One file, no server.

H2 runs in PostgreSQL compatibility mode, which is what lets the same tracker DDL work on both. The code branches on the URL in a handful of places (config.dataSource.url.contains("jdbc:postgresql")), treating H2 and PostgreSQL as one family and SQL Server as the other.

Overriding configuration

Spring Boot reads ./application.yml from the working directory and merges it over the one inside the jar. A minimal override:

server:
  port: 8080
  disable_lanid: true          # local passwords instead of Active Directory
  allow_registration: false
dataSource:
  driverClassName: org.postgresql.Driver
  username: g6portal
  password: <secret>
environments:
  production:
    dataSource:
      dbCreate: update
      url: jdbc:postgresql://db.internal:5432/g6portal?stringtype=unspecified
portal:
  bundled_modules_folder: "./bundled-modules"
grails:
  mail:
    host: smtp.internal
    port: 25

A jar started with no --spring.profiles.active runs in the production environment, so that is the block that matters. dbCreate: update lets the platform's own schema evolve on upgrade; the tracker tables are managed separately by the tracker code itself.

Shipping a preconfigured instance

Drop module packages into bundled-modules/ and each one that is not installed yet is imported at startup, before anyone logs in:

Bundled modules: found 1 package(s) in /home/you/g6portal/bundled-modules
Importing pages from .../uploads/modulemigration/livequiz
Importing page: livequiz:manage
...

This turns "unzip this and run it" into a real deployment story. Two limits are worth knowing before you rely on it:

  • A module that already exists is left completely alone. This is an install path, not an upgrade path — upgrading stays a deliberate act through the import screens, where a human sees the diff first.
  • It cannot grant roles. The import runs at boot with nobody logged in, so unlike the interactive import it cannot make you a Developer on what it installed. Grant yourself the role afterwards at /userRole/create.

05Roles: getting yourself in

The permission model is one table wide. Understand it now and section 9 will not surprise you.

A permission in g6portal is a UserRole row: (user, module, role). The role is a free string. There is no role registry, no hierarchy, no groups — a role exists because somebody typed its name into a grant and something else looks for that name.

The four rules

  1. Roles are per module.

    Agent on helpdesk means nothing on claims.

  2. Developer implies Admin, on that module only.

    Granting Developer on helpdesk makes user.modulerole('helpdesk') return ['Developer','Admin']. This is why a developer can reach a page whose allowedroles only lists Admin.

  3. Developer on a module unlocks that module's admin screens.

    The interceptor admits a Developer of the named module to /portalPage, /portalTracker and the builder. It is the role you give someone who is building the module, not someone who is using it.

  4. isAdmin only means "Admin everywhere" when enablesuperuser is on.

    With the setting off, a system administrator has the flags that test isAdmin directly and nothing more — modulerole() reports no role at all for a module they hold no grant on, and module pages will bounce them. This catches people out constantly. The setup screen ticks it for you; if you skipped it, add a Number setting named enablesuperuser with value 1, then log out and back in.

Roles are cached in the session

enablesuperuser, adminmodules and developermodules are computed once per session, and modulerole() is cached per user object. After changing your own roles or that setting, log out and back in — otherwise you will be debugging a permission that has already been granted.

06Build a module: the namespace

Everything from here to section 12 builds one worked example: a helpdesk with tickets that move through a small workflow.

Go to Admin → Module. A fresh instance has nothing:

  1. Create the module.

    New PortalModule, then a name. Lowercase, no spaces — this name goes into URLs (/helpdesk/ticket/list), into table names (trak_helpdesk_ticket_data) and into every role grant.

  2. Look at what the module page gives you.

    The show page is the module's control room: the export/import toolbar along the top, then its trackers, pages, roles, settings, trees, endpoints and files, each with an Add link that pre-fills the module for you. Use these links rather than the top-level admin screens — they save you typing the module name, and typing it wrong is the single most common beginner mistake.

  3. Grant yourself Developer on it.

    Click Add Developer. Module and role arrive pre-filled; pick yourself from the user search and save.

    Do this even as a system administrator

    With enablesuperuser on you would get in anyway — but the grant is what makes the module's Developer role real, and it is what gets exported when you package the module for someone else.

Create Defaults

Now press Create Defaults on the toolbar. In one click it gives the tracker everything it needs to be usable:

  • an Admin role;

  • New, Edit and Delete transitions, all restricted to Admin.

That is a working create/read/update/delete tracker. Everything in the next section turns it into a workflow.

08The workflow

Statuses are where a record can be. Transitions are how it moves, who may move it, and what they may edit on the way.

Statuses

A ticket needs two more states beyond New: In Progress and Resolved. Status tab → Create Status.

Now edit the status and set displayfields: the fields shown on a record while it sits in this status, in the order you drag them.

A status also carries editroles and editfields (inline editing without a transition), updateable and attachable flags, emailonupdate, and compositeStatuses for statuses that stand in for a group.

Roles

A tracker role is a name the tracker recognises. There are two kinds:

User Role
Matched against the user's module roles. A tracker role called Agent is satisfied by a UserRole row granting Agent on this tracker's module.
Data Compare
A Groovy rule evaluated against the record and the current user. This is how "the person who raised it" or "the assignee's manager" become roles.

Add Requester and Agent, both User Role.

Transitions

A transition answers four questions at once:

prev_status
Which statuses it can be run from. Empty means it creates a new record.
next_status
Which status the record lands in. Or tick same_status to leave it where it is.
roles
Who may run it. A user with none of these roles never sees the button.
editfields
Which fields the form offers. This is the transition's whole form definition.

The helpdesk workflow needs three more on top of the defaults:

TransitionFromToRolesEdit fields
AssignNewIn ProgressAgentassignee, priority, due_date
ResolveIn ProgressResolvedAgentdetails
ReopenResolvedNewRequester, Agentdetails
Create, then wire

Like statuses, a transition's role and status pickers are empty on the create form because they are populated from the tracker it does not yet belong to. Create each transition with just a name and a tracker, then open it for editing and wire it up.

See it, and edit it, as a graph

Workflow Graph on the tracker toolbar draws the whole state machine, and for anyone holding a Developer role on the tracker's own module it is also an editor.

Click a status or a transition and the panel above the graph becomes its editor:

Who may edit here

Editing writes tracker structure — columns, statuses, transitions — so the builder re-checks permission itself rather than trusting the interceptor: you need Developer on this tracker's own module, or to be a system administrator. Reading the graph is open to anyone who can reach the tracker.

09Using what you built

No code was written. The screens already exist.

The lesson in the buttons

Open a ticket. Which buttons you see is the whole permission model in one screen.

Tracker roles are satisfied by module roles

Before Agent was granted at /userRole, this page showed only Delete and Edit — the two Admin transitions. Assign appeared the moment the module role matched the tracker role by name. Defining a role on a tracker does not give it to anyone; a UserRole row does. When a transition button is missing, this is almost always why.

10Pages

Where you write actual code. A page is GSP in a database column with Groovy behind it.

Trackers give you generated screens. A page gives you a blank canvas: a dashboard, a report, an HTMX fragment, a JSON endpoint, a generated spreadsheet. Pages are how every g6portal module stops looking like a generated admin app.

Two kinds of page

Display
runable off. content is compiled as a GSP template and rendered into the site layout. Reached at /view/<module>/<slug>.
Runable
runable on. content is evaluated as a Groovy script and whatever it returns is the response. Reached at /run/<module>/<slug>.

That distinction is the one to keep straight. A display page returns markup; a runable page returns a value, which the render mode then interprets.

What runs, in order

  1. Datasources.

    Each PortalPageData row holds Groovy that must return a SQL string. The string is run, and the rows land in datas.<name>. A :name placeholder in the SQL is bound from params. Tick return one for a single row instead of a list.

  2. Preprocess.

    Groovy, with datas now in scope. Whatever it returns arrives in the view as pp. This is where the real work belongs — queries, aggregation, permission decisions — so the view stays a view.

  3. Content.

    For a display page, compiled as GSP with pp and datas available. For a runable page, evaluated as Groovy.

A worked example

The helpdesk needs a landing page: counts by status, a table of tickets, links onwards. Create it from the module page's Add Page, so the module is filled in for you.

The preprocess does the work:

// Runs before the page renders. Whatever it returns arrives in the view as `pp`.
def T = g6portal.PortalTracker

def rows = T.raw_rows('''
    select id, subject, priority, due_date, record_status as status, assignee
      from trak_helpdesk_ticket_data
     order by id desc
''') ?: []

def counts = [:]
rows.each { r -> counts[r.status] = (counts[r.status] ?: 0) + 1 }

def names = [:]
rows*.assignee.findAll { it }.unique().each { uid ->
    names[uid] = g6portal.User.get(uid as Long)?.name
}

return [rows: rows, counts: counts, names: names, total: rows.size()]

11Menus and navigation

Until you wire a menu, a module is reachable only by typing a URL.

Navigation lives in two trees, both owned by the module portal, because the taglibs hardcode that: portal/main_menu is the header megamenu, and portal/<module>_menu is a module's sidebar. You could build the nodes by hand at /portalTree. Don't — declare them in the module package instead, and the portal builds and maintains both trees for you.

menulist.json

One file at the package root, beside pagelist.json:

{
    "label": "Helpdesk",
    "icon": "life-preserver",
    "items": [
        { "name": "Helpdesk home",  "link": "page:helpdesk:dashboard",
          "icon": "speedometer2", "group": null },
        { "name": "Raise a ticket", "link": "link:/helpdesk/ticket/create",
          "icon": "plus-circle",  "group": null },
        { "name": "All tickets",    "link": "tracker:helpdesk:ticket",
          "icon": "card-list",    "group": "Authoring" }
    ]
}

Icons are Bootstrap Icons names without the bi- prefix. Entries sharing a group are collected under one heading; null puts the entry directly under the module. Two optional keys, mainrole and hiderole, gate an entry by role.

Link forms

page:<module>:<slug>[:arg1[:arg2[:arg3]]]   a portal page
tracker:<module>:<slug>                     a tracker's list screen
run:<module>:<slug>                         a runable page
file:<module>:<slug>                        a file download
link:/any/path                              anything else

What gets built

Importing a package that carries menulist.json gives the module a column in the header megamenu and a sidebar of its own. The sidebar only appears on screens that ask for it: set side_menu to the module name on the pages and trackers that should carry it — the taglib appends _menu itself.

Ownership, and why it matters

Every node built from a declaration is stamped with its module in the node's data field, and matching is done by that stamp, never by name. So:

  • Renaming an entry updates it rather than leaving a duplicate behind.
  • Re-importing rebuilds the module's nodes to match the declaration — including deleting entries the declaration has dropped. The menu always reflects the installed version.
  • Reordering items reorders the menu.
  • Nodes an administrator added by hand carry no stamp and are never touched. Neither is any other module's column.
Two things menus do not do

Menu visibility is not access control. An entry shows to anyone the node's mainrole / hiderole allow; whether the page behind it opens is decided by that page's own allowedroles. Gate the page, not just the menu.

A removed module keeps its menu. Deleting a PortalModule row does not sweep up the nodes it contributed. Remove them at /portalTree, or re-import with an empty items list.

12Packaging a module

A module becomes a file, and the file is the thing you commit, review and ship.

Export

The module page's toolbar carries the export controls. Tick what the package should include, then Export.

OptionAddsTick it when
— (default)trackerlist.json, pagelist.json, pages/*.gsp, settinglist.jsonAlways attempted. Each file is written only if the module actually has something of that kind, so a small package is a short one.
Filesfilelinklist.json and the file bodiesThe module ships templates or images.
Treestreelist.jsonThe module owns a tree of its own, beyond the menus.
Menusmenulist.jsonNearly always — otherwise the module installs unreachable.
Useruserrolelist.jsonThe role grants should travel too. Usually not, between environments.

The result lands in uploads/modulemigration/<module>/ and as <module>.zip beside it. The archive's entries sit at the ZIP root — there is no wrapping directory, and the importer expects it that way.

helpdesk.zip
  trackerlist.json      # trackers with fields, statuses, roles, transitions
  pagelist.json         # page flags: slug, module, published, render, allowedroles...
  menulist.json         # menu entries          (only when Menus was ticked)
  settinglist.json      # module-scoped settings (only when there are any)
  pages/
    content_dashboard.gsp   # page content, one file per page
    pp_dashboard.gsp        # page preprocess, where there is one

Page content lives in files rather than inside the JSON, which is what makes a package reviewable: a diff of pages/content_dashboard.gsp reads like a diff of any other template.

Import

Import never applies immediately. It stages the package, compares it with what this server already holds, and shows you a diff:

Three things about the preview are worth knowing:

  • The Add this module's menu entries checkbox is ticked by default. Untick it to take the module without disturbing a menu somebody has curated; the import log records that the entries were left out. The diff always shows menulist.json either way, so it compares like with like.
  • Endpoints are only imported by a system administrator. An endpoint's target is a program this server executes, so endpointlist.json is skipped for everyone else — and the console says so.
  • The import gives the importing user Developer on the module. That is the difference between importing through the screens and dropping a package in bundled-modules/.

Every import is recorded at /portalModule/importlogs: who, when, which options, what remarks, and the diff that was shown.

Keeping the package as source

Exporting from a running portal is fine for moving a module between environments. For a module you are actively developing, invert it: keep the package in the repository and treat the portal as the thing you install into. The livequiz module in modules/livequiz/ is the reference for this pattern:

modules/livequiz/
  gen_trackers.py     # generates trackerlist.json
  gen_pages.py        # generates pagelist.json (flags only)
  menulist.json       # hand-written
  build.sh            # runs both generators, then zips
  pages/
    content_<slug>.gsp
    pp_<slug>.gsp

The JSON is generated because the package format repeats the same statuses, roles and transitions for every tracker, and hand-copying that across five of them invites drift. Page content is never generated — it lives in pages/ as ordinary files you can edit, diff and review, and the importer reads them directly. ./build.sh produces the ZIP; upload it at the import screen, or drop it in bundled-modules/ for a fresh instance to pick up at boot.

13The rest of the platform

Everything else in the Admin menu, and when you would reach for it.

Settings

Typed configuration rows, optionally scoped to a module. Read them from anywhere with PortalSetting.namedefault('name', fallback), which returns the fallback when the row is absent — so a module can ship with sensible behaviour and let a site override it. Lookup falls back from module.setting to the global setting.

Settings you will meet:

enablesuperuser
System administrators count as Admin of every module. Section 5.
portal.whitelist
Controller/action pairs the interceptor lets through unchecked.
portal.module_whitelist
Modules reachable while impersonating another user.
migrationfolder
Where module export and import stage their files. Defaults to ./uploads/modulemigration.

Maps a field type name onto module.slug of another tracker, for BelongsTo-style relations.
emailpagerror
An address to mail when a page throws.
download_module_whitelist
Modules whose files are downloadable without a role check.

Files

File (/fileLink) is one uploaded file with a slug, a module and its own allowedroles, served from /download/<module>/<slug>. Tracker File fields create these rows for you. File Manager (/portalFileManager) exposes a folder on disk as a browsable tree instead.

Scheduler and e-mail

A PortalScheduler row names a list of page slugs and an hour / day-of-week / day-of-month pattern, and runs those pages on that schedule. Because the unit of work is a page, a scheduled job is written exactly like any other runable page — there is no separate job API to learn. PortalEmail does the same for mail, with a page as the body.

Endpoints

Portal pages return a String, so they cannot carry a binary wire protocol. PortalEndpoint is the escape hatch: it hands the raw request to a handler and streams the reply back, with the portal doing authentication in front. Served at /svc/<module>/<slug>/..., with everything after the slug belonging to the handler.

Handlers
CGI executes target as a CGI program; Proxy forwards to target as an upstream base URL.
Auth modes
Basic (what git and hg clients send), Token (a shared secret in ?token= or X-G5-Token), Session (an existing portal login), None.
Why superuser only

An endpoint's target is a program this server executes. Being able to edit one is being able to run anything as the portal's account. The interceptor enforces the restriction; hiding the menu entry is only cosmetic. Note that serve is the one action exempt from the interceptor entirely — a protocol client cannot follow a redirect to a login form — so each endpoint authenticates itself.

Errors, audit and impersonation

Error (/portalErrorLog) is where swallowed exceptions go, with the params, user, controller and module that produced them.

PortalAuditTrail records one row per request — controller, action, params, URI, IP, user agent, user, and the real user when someone is impersonating. It is written before any permission check, so it captures attempts as well as successes, and it has no opt-out from module code. A page that polls writes a row per poll; a room of fifty phones polling every three seconds is roughly sixty thousand rows an hour. Throughput is not the problem; growth is. Plan housekeeping for anything that polls.

An administrator can switch into another user's session from the user screen, to see exactly what they see. While impersonating, the module whitelist and the real user's own admin list still apply, so impersonation cannot be used to reach a module the administrator could not reach anyway.

Search and branding

PortalSearch indexes tracker records for the header search box; a tracker opts in through its Index tab. /branding sets the logo, favicon, product name and colours — system administrators only.

14The security model

What is checked, where, and the places it is easy to get wrong.

Where the checks live

  • SecurityInterceptor runs before every controller except login, /setup, the OAuth callbacks and portalEndpoint.serve. It resolves the user, writes the audit row and decides admission per controller family.
  • Pages are matched on published, requirelogin and allowedroles, the last against user.modulerole(module). Running a page also re-checks against the resolved page, so addressing a page by id cannot bypass the check.
  • Trackers are matched on require_login, allowedroles, and the anonymous_list / anonymous_view flags. Beyond admission, a transition's own roles decide whether its button is offered at all.
  • Files are matched on the FileLink's own allowedroles, then on module roles, then on the download whitelist. A file attached to a tracker record inherits that record's access.
  • Structural edits re-check themselves. The tracker builder and the endpoint screens do not trust the interceptor, because its "Developer of any module" shortcut is deliberately wide for reading and far too wide for writing.

Making something anonymous

Anonymous access is the pair requirelogin: false plus published: true on a page, or anonymous_list / anonymous_view on a tracker. Both halves are required; one alone does nothing.

Five things to hold on to

  1. A missing button is a role problem nine times in ten.

    Tracker role names must be matched by UserRole grants on the same module.

  2. Gate the page, not the menu.

    Hiding a menu entry hides nothing. The URL still works if the page allows it.

  3. Anything a client sends must be re-checked server-side.

    Anonymous pages in particular: verify state, ownership and timing on every submission, and make replays harmless.

  4. A Developer on one module is not a developer on another.

    Except where enablesuperuser is on and the user is a system administrator.

  5. Page and tracker code runs as the server.

    content, preprocess, field_options and role rules are all evaluated Groovy. Granting Developer on a module is granting the ability to run code on the server. Treat the role accordingly.

Day to day

export JAVA_HOME=$HOME/.sdkman/candidates/java/11.0.24-tem

./gradlew bootRun          # dev server on :9090, reload on change

Tests get their own database

The test environment points at jdbc:h2:mem:testDb, not at ./g6db. That is deliberate: sharing the file meant a test run wrote to real data, and could not run at all while the application was up, because H2 locks the file to one process.

Things that will bite you

  • The CSP blocks CDNs. SecurityHeadersInterceptor sets script-src 'self', and a blocked script fails silently. Vendor libraries into grails-app/assets/.
  • The asset compile dominates the build. A clean bootJar is a few minutes, most of it minifying assets.
  • Two databases, one DDL. H2 runs in PostgreSQL mode and the code treats the two as one family, branching only for SQL Server. New DDL needs both branches.
  • Encoding in GSP-generated JSON. Serialise with JsonOutput.toJson in the controller rather than encodeAsJSON() in the view — the view's HTML codec turns the output into &quot;-riddled markup that breaks the script block.
